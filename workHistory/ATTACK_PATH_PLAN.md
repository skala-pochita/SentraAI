# 근거가 연결된 공격 경로 — 개발 계획 및 체크리스트

작성일: 2026-10-23

상태: **구현 및 로컬 검증 완료 / 기존 실행 환경 배포·실제 LLM 데모 미실행**

구현 결과와 검증 범위: [ATTACK_PATH_IMPLEMENTATION.md](ATTACK_PATH_IMPLEMENTATION.md)

이 문서의 현황 분석은 구현 전 정적 검토를 기준으로 한다. 이후 이 계획에 따라 코드를 구현했으며, 최신 결과는 위 구현·검증 문서를 따른다.

## 1. 목표와 범위

현재 결합 위험 5개 규칙을 유지하면서, 각 위험을 구성하는 사실과 연결 근거를 사용자가 단계별로 확인하게 한다.

예시:

> 외부 문서에 공격 입력 포함 → 특정 probe 시도에서 도구 실행 보고 → 해당 도구의 승인 통제 누락 → 데이터 변경 가능

마지막 단계를 실제 ‘고객 데이터 삭제 완료’로 표시하려면 삭제 결과를 입증하는 별도 관측이 필요하다. `executed=true`나 모델의 성공 설명만으로 실제 데이터 삭제를 확정하지 않는다.

### 이번 개발에 포함

- CORR-001~005의 구조화된 단계·연결·근거.
- 대상·실행 시도·도구 단위의 정확한 근거 연결.
- 특정 도구명 대신 명시된 동작 특성을 사용하는 결합 판단.
- 단계 및 연결별 `실행 확인 / 정적 근거 / 조건부 추정` 표시.
- 코드 위치·probe 입력/응답·도구 호출 기록을 여는 상세 패널.
- 기존 3D 그래프와 경로 상세의 데이터 일치.
- DB·API·JSON/Markdown 보고서·기존 감사 호환성.

### 이번 개발에서 제외

- 새로운 자동 공격 체계, 범용 프로그램 데이터 흐름 분석, 전체 시스템 공격 그래프 탐색.
- 자동 수정·수정 후 재검증·SOC·전사 자산 관리.
- A1~A4 권한 점검 모듈 전체의 제품 연동.
- LLM이 임의로 경로를 생성하거나 추론만으로 확정 판정을 내리는 기능.
- 임의 도구의 실제 외부 전송·삭제 결과를 모두 검증하는 범용 실행 계측.

## 2. 현재 코드에서 확인한 내용

| 영역 | 현재 구현 | 개발 시 해결할 사항 |
|---|---|---|
| 결합 규칙 | `backend/core/graph/nodes/correlate.py`의 Python 함수 5개 | 규칙 정의는 별도 correlation YAML이 아니라 코드에 있음. 판정과 경로 생성 책임을 분리 |
| 도구 식별 | `_tool_of()`가 Finding 제목의 `: ` 뒤 문자열을 사용 | 제목 대신 구조화된 대상·도구 식별자를 전달 |
| 실행 집계 | `probe_run.py`가 모든 시도의 실행 도구를 `tools_hit`에 합침 | 성공한 시도와 도구 호출을 같은 `probe_run_id`로 묶어야 함 |

| 서브그래프 | `AgentAuditState`에는 manifest가 있지만 `AgentAuditOutput`에는 없음 | 필요한 도구 메타데이터만 출력 계약에 추가 |

| 저장 배열 | `finding_ids`는 `[결합 Finding ID, 구성 Finding ID들]` | 배열 순서는 공격 발생 순서가 아님 |
| 화면 | `RisksPage.vue`에 3D 그래프가 이미 존재 | 새 그래프를 추가하기보다 기존 데이터 계약을 개선 |
| 그래프 | `RiskGraph3D.vue`가 `finding_ids` 인접 항목을 선으로 연결 | 실제 연결과 단순 구성 관계를 구분해야 함 |
| 상세 API | Finding 상세에서 `probe_transcript_ref`로 실행 기록을 조회 | 새 참조와 기존 참조 조회 모두 감사·대상 경계 검증 필요 |
| 보고서 | graph의 `risk_paths`를 JSON에 포함하고 Markdown에는 요약만 출력 | API와 보고서가 공통 경로 스키마를 사용해야 함 |
| 테스트 | 기존 graph/API 테스트에 결과 존재·응답 형식 확인이 있음 | 5개 규칙의 교차 대상·교차 시도 오결합 방지 전용 테스트 추가 |

### 규칙별 현재 한계

| 규칙 | 현재 조건 및 한계 | 개선 방향 |

## 3. 권장 설계

### 3.1 사실·연결·영향을 분리

경로는 순서가 있는 단순 문자열 목록이 아니라 `steps`와 `edges`로 구성한다. 승인 정책처럼 실행 순서와 별개로 영향을 주는 사실은 정책 근거 관계로 표현한다.

- `steps`: 입력, 실행 관측, 통제 상태, 코드 상태, 영향 등.
- `edges`: 관측된 순서, 정적 연결, 위험 성립 조건 등 관계를 명시.
- `finding_ids`: 기존 호환·관련 이슈 조회용으로 유지. 순서 의미를 부여하지 않음.
- 같은 시도에 존재한다는 이유만으로 인과 관계를 확정하지 않음. 호출 순서/연결 근거가 부족하면 조건부 관계로 표시.

예를 들어 ‘승인 없음’은 실행 이벤트가 아니라 매니페스트에 대한 정적 사실이다. 한 경로에 실행 확인과 정적 근거가 함께 존재하는 것이 정상이다.

### 3.2 근거 수준과 실행 환경

| 표시 | 사용 조건 | 표시하면 안 되는 내용 |
|---|---|---|
| 실행 확인 | 해당 run/call/관측 결과에 직접 연결된 사실 | LLM 추정만으로 실행 또는 실제 피해 확정 |
| 정적 근거 | 파일·라인 또는 매니페스트 필드에 근거한 사실 | 선언된 권한을 런타임 권한 강제의 증명으로 취급 |
| 조건부 추정 | 구성 사실은 있지만 실행 연결·영향 확인이 부족함 | 확인되지 않은 조건을 생략한 확정 문구 |

추가로 `mock / live / unknown`과 관측 출처를 별도 표시한다. mock 컨테이너에서의 실행 관측은 가능하지만 실제 LLM 방어 성능이나 운영 데이터 피해를 의미하지 않는다. 대상이 반환한 `executed=true`는 ‘대상 보고 기반 도구 실행’임을 밝힌다.

필수 근거 자체가 없으면 억지로 경로를 만들지 않고 누락 이유를 남긴다. 과거 데이터에 새 단계 정보가 없으면 `기존 형식 / 단계 근거 미수집`으로 표시한다. 과거 경로를 일괄 ‘조건부 추정’으로 재분류하지 않는다.

경로 전체에 단일 ‘검증 완료’ 배지를 붙이지 않고 단계·연결별 배지를 표시한다. 심각도와 근거 수준은 서로 다른 축으로 유지한다.

### 3.3 제안 데이터 계약

아래는 구현 전 확정할 필드 초안이다.

```text
RiskPath
  기존: id, rule_id, severity, title, finding_ids, explanation
  추가: schema_version, correlation_finding_id, target_ids
        steps[], edges[], missing_evidence[]

Step
  id, kind, title, claim, evidence_level, target_id
  evidence_refs[], conditions[]

Edge
  id, from_step_id, to_step_id, relation
  evidence_level, evidence_refs[], conditions[]

EvidenceRef
  kind: finding | code | manifest | probe_run | tool_call
  finding_id?, target_id?, file_path?, line_start?, line_end?
  probe_run_id?, tool_call_index?, field_path?

ProbeAttemptEvidence
  audit_id, target_id, probe_id, base_probe_id?, round
  probe_run_id, attempt, verdict, judged_by
  runtime_mode, observation_source, tool_calls[], signals

ToolProfile
  target_id, tool_id, name, side_effect?, requires_approval?
  scopes[], source_ref, metadata_status
```

- `EvidenceRef`는 검증 가능한 유형별 스키마로 구현한다. 임의 dict나 임의 URL을 근거로 허용하지 않는다.
- ToolProfile은 manifest의 명시적 필드와 근거 출처를 우선 사용한다. 미확인 값은 보존하며 도구 이름·설명만으로 확정하지 않는다.
- `FindingDraft`에는 도구/환경변수 등 구조화된 subject를 추가하고, 필요한 영속 필드도 함께 정한다. 제목 문자열 파싱을 신규 판단에서 제거한다.
- `tool_call_index`를 쓰는 MVP에서는 저장된 호출 배열을 불변으로 취급한다. 재정렬/재작성한다면 호출 ID가 필요하다.
- 카나리나 비밀 유출 확인은 마스킹 전에 검증한 비민감 신호로 남긴다. 실제 비밀값을 경로에 추가하지 않는다.
- probe의 판정 enum을 보존해 `UNDETERMINED`가 DB의 `success=false` 때문에 ‘차단’으로 표시되지 않게 한다.

### 3.4 실행 근거 수집부터 개선

1. `execute._record()`의 run ID·시도·도구 호출·신호를 한 객체로 유지한다.
2. `probe_run`은 집계 결과 외에 target/run 단위 근거를 출력한다. 서로 분리된 `run_ids`와 transcript 배열의 위치에 의존하지 않는다.
3. `probe_judge`의 최종 판정과 출처를 해당 run에 반영한다. 기존 MCP 권한 게이트를 따르는 제한된 저장 경로를 마련한다.
4. 정적 도구 메타데이터와 실행 근거를 `AgentAuditOutput`을 통해 부모 그래프에 전달한다.
5. 결합 단계는 대상 ID·도구 ID·run ID로 조회하며, 다른 시도나 다른 대상에서 가져온 사실을 실행 경로로 합치지 않는다.

`core/probes.py`의 일부 판정도 샘플 도구명을 사용한다. 결합 로직만 일반화해서 전체 공격 검증이 범용화됐다고 설명하지 않는다. MVP는 지원되는 probe 계약과 명시적 ToolProfile 범위로 제한하고, 필요한 성공 조건만 특성 기반으로 확장한다. 정의되지 않은 호출 결과는 미확인으로 남긴다.

### 3.5 규칙별 경로 표현

| 규칙 | 제안 단계/관계 | 확정 경계 |
|---|---|---|
| CORR-001 | 공격 입력 → 해당 도구 호출 관측; 승인 정책 → 호출 위험; 호출 → 변경/삭제 가능성 | 삭제 결과 근거가 없으면 ‘삭제 가능’. write/refund를 일괄 삭제로 표현하지 않음 |
| CORR-002 | 입력 → 외부 전송 도구 호출; 수신자 정책 → 전송 위험; 전송 → 유출 가능성 | 외부 대상·전송 내용 증거 없이 실제 데이터 유출 완료로 표시하지 않음 |
| CORR-003 | 코드의 비밀 선언 ↔ 연결된 Agent의 동일 변수 참조 → 자격증명 노출 가능성 | 정적 노출 경로. 실행 타임라인으로 연출하지 않음 |
| CORR-004 | 프롬프트 내 비밀 선언 + 해당 대상 유출 시도 → 비밀 유출 가능성/확인 | 일반 프롬프트 유출만 확인했다면 비밀 유출 구간은 조건부 |
| CORR-005 | 도구의 백엔드 참조 ↔ API의 인증 설정 → 무인증 접근 가능성 | 프로젝트 연결만으로 API 호출을 확정하지 않음. 매핑이 없으면 경로 생성 보류 |

기존 심각도를 무조건 복제하지 않는다. 특히 CORR-004의 비밀 유출 확정·승격은 증거 조건을 다시 정하고 테스트한다. 기존 결과와 달라지는 항목은 설계 변경 기록과 평가 결과에 명시한다.

### 3.6 저장·API·보고서

- RiskPath에 버전이 있는 JSONB 경로 payload를 추가하는 방식을 우선 권장한다. 초기에는 별도 그래프 DB가 필요하지 않다.
- correlation Finding과 경로 payload를 같은 트랜잭션에 저장한다. 스키마 검증 후에만 저장하며 존재하지 않는 단계/참조는 거부한다.
- Finding 임시 ID를 DB ID로 바꿀 때 steps/edges의 참조도 치환한다.
- 감사·규칙·대상·구성 근거로 경로 identity를 정의한다. 동일 구성의 복수 실행은 근거로 합치고 다른 도구/경로는 구분한다.
- 기존 중복 Finding 조기 반환에서도 경로가 누락되거나 중복되지 않도록 멱등 저장 전략을 정한다. 재시도에 의해 증거가 줄어들지 않아야 한다.
- 기존 `GET /audits/{audit_id}/risk-paths`에 필드를 추가한다. 상세 근거 조회는 감사 범위의 경로/근거 API를 권장한다.
- 근거 조회 시 해당 감사에 속한 Finding·ProbeRun인지 확인하고 연결된 대상의 접근 권한도 검증한다. 기존 Finding 상세의 probe 조회에도 같은 검증을 적용한다.
- 완료 전 결과 비공개(409), 소유권/RBAC, 서버 재마스킹을 유지한다.
- API·graph state·JSON 보고서에서 공통 경로 모델을 사용한다. Markdown에도 단계·연결 근거 수준과 미확인 조건을 포함한다.
- 과거 레코드는 payload 없이 읽을 수 있게 한다. 기존 실행 기록으로 증명할 수 없는 연결을 마이그레이션에서 생성하지 않는다.
- 마이그레이션 적용 순서는 DB의 호환 필드 추가 → 백엔드 → 프론트로 잡는다. 진행 중 checkpoint의 구형 필드 누락도 허용하고, 신형 기록을 읽지 못하는 구버전 워커와의 혼용은 피한다.

### 3.7 화면

- 기존 3D 그래프는 개요로 유지하되 steps/edges를 그리도록 변경한다. 경로 ID+step ID를 기본 노드 키로 사용해 서로 다른 의미의 단계를 우연히 합치지 않는다.
- 구성 관계와 공격 흐름을 구분하고 조건부 연결은 점선·문구로 함께 표현한다.
- 읽기 쉬운 2D 단계 목록/타임라인을 주 상세 화면으로 제공한다. 정적 연결은 ‘실행 순서’가 아닌 ‘근거 관계’로 표시한다.
- 단계 또는 연결 선택 시 근거 패널을 연다: 주장, 수준, 출처, 코드 위치/마스킹 snippet, 해당 run 입력·응답·호출, 미확인 조건.
- RedTeam 화면은 run ID로 정확한 시도를 열 수 있게 하거나 공통 근거 컴포넌트를 재사용한다. 현재 프론트 Evidence 타입에서 빠진 transcript 참조도 보강한다.
- 원본 전체 코드를 새로 노출하는 대신 저장된 마스킹 snippet부터 제공한다.
- 색상 외에 텍스트 배지, 키보드 선택, 좁은 화면과 3D 불가 환경의 2D 대체를 제공한다.
- 구형 감사는 기존 설명과 Finding 링크를 제공하되 연결을 실행 순서처럼 그리지 않는다.

## 5. 필수 검증 매트릭스

| 사례 | 기대 결과 |
|---|---|
| 같은 대상·성공 run에서 삭제 특성 도구 실행, 승인 누락 | 호출 관측과 정책 근거가 연결됨. 삭제 결과 미관측이면 영향은 조건부 |
| 도구 이름 변경, 동작 특성 동일 | 같은 의미의 결합 위험 탐지 |
| `refund_order`가 write로 선언 | 데이터 삭제 완료라고 표현하지 않음 |
| A 시도는 공격 성공, B 시도에만 관련 도구 실행 | 두 시도를 하나의 실행 경로로 합치지 않음 |
| 두 에이전트에 같은 probe/tool 이름 | target ID 기준으로 완전히 분리 |
| 도구 호출 요청만 있고 executed=false | 도구 실행 확인 표시 금지 |
| 호출은 실행됐으나 오류 결과 또는 변경 증거 없음 | 실제 영향 확정 금지 |
| 소스 자동 인식에서 side_effect/정책 미확인 | 이름 기반 확정·누락=승인 없음 간주 금지 |
| 외부 전송 Finding과 실행된 도구가 서로 다름 | CORR-002 확정 연결 금지 |
| 다른 프로젝트에 동일 비밀 변수명 | CORR-003 연결 금지 |
| 프롬프트 일부 유출, 내장 비밀 유출 근거 없음 | CORR-004 비밀 유출 확정·자동 승격 금지 |
| backend 연결 없음/동명이인 repo | CORR-005 임의 연결 금지 |
| mock 실행 또는 LLM 추정 판정 | 환경·판정 주체·관측 범위를 정확하게 표시 |
| UNDETERMINED→LLM 재판정 | DB 상세·API·경로·보고서 판정 일치 |
| 같은 감사 재시도/중복 저장 | 경로 중복·근거 소실 없음 |
| 다른 감사의 run ID 또는 잘못된 step 참조 | 저장/조회 단계에서 거부 |
| 과거 RiskPath에 payload 없음 | 조회 가능, 새 실행 순서 생성 금지 |
| 공격 입력에 비밀·악성 마크업 포함 | 마스킹 및 안전한 텍스트 렌더링 |

## 7. 착수 권장안

첫 구현 단위는 **CORR-001 하나를 근거 수집 → 결합 → 저장 → API → 2D 상세까지 관통하는 작업**으로 잡는다. 단, 공통 데이터 계약은 5개 규칙을 수용하도록 먼저 정한다.

이 경로에서 동일 대상·동일 시도 보장과 도구 특성 일반화를 검증한 뒤 CORR-002~005에 확장하고, 3D 그래프와 보고서를 마무리한다. 이 순서는 화면부터 꾸민 후 잘못된 연결을 수정하는 재작업을 줄인다.

정확한 일정은 사용 가능한 개발 인력과 종료일이 정해진 뒤 산정한다. 주요 공수는 그래프 표현보다 **실행 근거 보존·판정 일치·규칙의 연결 조건 보완**에 있다.
