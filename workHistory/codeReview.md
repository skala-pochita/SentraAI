## 3. 실제 코드에서 좋았던 부분

### A. Kafka Consumer의 파티션별 동시 처리

파일: `backend/core/kafka/consumer.py`

이번 PR에서 내가 특히 좋게 본 코드야.

기존에는 메시지를 하나씩 처리했는데, 이번에는 파티션별로 작업을 분리했어.

```
inflight: dict[Any, tuple[asyncio.Task[None], ConsumerRecord]] = {}batch = await consumer.getmany(    timeout_ms=500,    max_records=max(1, concurrency))
```

그리고 작업 중인 파티션은 `pause()`하고 처리가 끝나면 `resume()`하는 구조야.

이 설계의 장점은 다음과 같아.

- 서로 다른 파티션은 병렬 처리 가능
- 같은 파티션 내부의 순서 유지
- 작업이 길어져도 poll을 계속 수행
- 완료된 메시지만 offset 커밋

특히 단순히 `asyncio.gather()`를 도입하는 것보다 Kafka의 파티션과 offset을 고려했다는 점이 좋아.

### B. 업로드 파일 보안 검증

파일: `backend/core/project_upload.py`

이 부분도 상당히 괜찮았어.

- ZIP 경로 탈출 방지
- 심볼릭 링크 차단
- 암호화 ZIP 차단
- 중복 경로 차단
- 압축 해제 용량 제한
- 실제 압축 해제 크기 재검증

특히 선언된 압축 크기만 믿지 않고 실제 읽은 바이트를 계산하는 부분은 좋은 선택이야.

```
while chunk := source.read(64 * 1024):    actual += len(chunk)    if actual > MAX_EXPANDED_BYTES:        raise AppError(...)
```

보안 감사 서비스를 만드는 프로젝트에서 업로드 자체가 공격 진입점이 될 수 있다는 점을 고려한 설계야.

### C. 병렬 Finding 저장

파일: `backend/core/graph/nodes/correlate.py`

여기서는 구성 Finding을 먼저 병렬 저장하고, 이후 상관관계 Finding을 저장하는 방식을 선택했어.

이유도 합리적이야.

상관관계 Finding은 다른 Finding의 ID를 참조하기 때문에 선행 데이터가 필요하거든.

단순 병렬화가 아니라 데이터 의존성을 이해하고 순서를 나눈 점을 높게 평가해.

## 4. 개선이 필요한 부분

여기부터는 조금 냉정하게 볼게. 실제 운영 환경을 생각하면 개선할 지점이 있어.



우선 개선

&#x20;A. Redis 락의 원자성 문제



파일: `backend/core/redis/locks.py`

현재 락 해제 코드는 다음과 같아.

```
if await r.get(key) == audit_id:    await r.delete(key)
```

문제는 두 작업 사이에 다른 작업이 개입할 수 있다는 거야.

예를 들어 다음 상황이 발생할 수 있어.

1. A 감사가 락 소유자인지 확인
2. A의 락이 만료
3. B 감사가 새로운 락 획득
4. A가 `delete()` 실행
5. B의 락까지 삭제

이건 전형적인 TOCTOU 경쟁 조건이야.

이미 `_RELEASE`라는 Lua 스크립트를 선언해 놓았지만 실제 해제 함수에서는 사용하지 않고 있어.

개선 방향: Redis Lua Script를 이용해 소유자 확인과 삭제를 하나의 원자적 연산으로 처리하는 게 좋아.

락 연장도 마찬가지로 `GET`과 `EXPIRE`를 분리하지 말고 원자적으로 처리하는 걸 추천해.



우선 개선

&#x20;B. Kafka 메시지 처리 Lease



파일: `backend/core/kafka/consumer.py`

현재 heartbeat는 다음과 같아.

```
await r.set(    f"kafka:processed:{message_id}",    f"processing:{WORKER_ID}",    xx=True,    ex=LEASE_S)
```

여기서 `xx=True`는 키가 존재하는지만 확인해.

현재 작업자가 여전히 해당 메시지의 소유자인지는 확인하지 않아.

만약 기존 작업자의 Lease가 만료되고 다른 작업자가 메시지를 획득했다면 이전 작업자의 heartbeat가 새로운 작업자의 소유권을 덮어쓸 가능성이 있어.

개선 방향:

- 메시지 획득 시 고유한 owner token 발급
- heartbeat에서 현재 owner token 일치 여부 확인
- Lua Script로 소유권 확인과 TTL 연장 원자화

이 부분은 Kafka의 중복 처리 방지라는 프로젝트의 핵심 기능과 직접 연결돼.



추가 검증 권장

&#x20;C. 병렬 처리의 테스트 범위



이번에 병렬화를 상당히 많이 도입했어.

그런데 정상적인 상황에서 동시에 실행되는지만 검증하는 것과 장애가 발생했을 때 안전한지는 다른 문제야.

추가하면 좋은 테스트는 다음과 같아.

| 테스트             | 검증 목적          |
| --------------- | -------------- |
| Worker 강제 종료    | Lease 만료 후 재처리 |
| Redis 일시 장애     | 중복 처리 및 복구     |
| Kafka Rebalance | offset 유실 방지   |
| DB 저장 실패        | Finding 중복 방지  |
| LLM 동시 호출 실패    | 예산 및 결과 일관성    |

특히 `asyncio.gather()`를 사용하는 부분은 실패한 작업이 발생했을 때 전체 작업이 어떤 상태가 되는지 확인해야 해.

## 6. 취업 관점에서 이 프로젝트를 어떻게 평가하느냐?

이 부분이 사실 가장 중요하다고 생각해.

현재 프로젝트에서 네가 담당한 영역은 일반적인 신입 백엔드 지원자의 CRUD 프로젝트와는 차이가 있어.

내가 면접관이라면 다음과 같은 질문을 할 것 같아.

| 면접 질문                             | 확인하려는 역량  |
| --------------------------------- | --------- |
| Kafka에서 At-least-once를 선택한 이유는?   | 메시징 이해도   |
| 중복 메시지를 어떻게 방지했는가?                | 분산 시스템    |
| Redis Lease가 만료되면 어떻게 되는가?        | 동시성       |
| Kafka Rebalance가 발생하면 어떻게 대응하는가?  | 장애 대응     |
| 왜 Finding 저장에 병렬 처리를 적용했는가?       | 성능 최적화    |
| Docker 격리 환경에서 호스트 접근을 어떻게 차단했는가? | 보안 설계     |
| LLM 비용을 어떻게 제한하는가?                | AI 서비스 운영 |

이 질문에 코드와 설계 의도를 연결해서 설명할 수 있다면 상당히 좋은 평가를 받을 수 있어.

특히 네가 Java/Spring을 주력으로 공부해 왔다는 점에서 Python 기반의 비동기 백엔드 경험까지 보여줄 수 있다는 것도 장점이야.
